> **本文件自包含**——执行者读 [folderActions.js](../../../src/services/folderActions.js) 的 `getFolderData` + 本文档即可动手。

**Goal:** 新增 `findFolderByPath(root, path)` 纯函数,取代 `foldersData.get(path)` 的「查询」用途,为 **T06(删 foldersData Map → 单 ref 持树)** 铺路。

**Why:** `foldersData` Map 现在身兼两职:① path→folder **查询**;② Vue **代理陷阱收口**(set 原始 folder → get 取代理)。T05 先把「查询」职责解耦到纯函数(从 `rootFolder` 树找),T06 再删 Map(连代理陷阱一起消灭)。**分两步是为降低 T06 高风险:先确认查询能脱离 Map,再删 Map。**

**关键风险(务必先验证):** 迁移前必须确认 **Map 与 rootFolder 树同步**(除 ALL_MEDIA 外,Map 里的 folder 都在树里)。若不同步,查询结果会变 → bug。见第三节。

**Architecture:** `findFolderByPath` 递归在 `rootFolder.subFolders` 树里按 `path` 匹配;替换 [folderActions.js](../../../src/services/folderActions.js) 的 2 处查询 `.get`;**代理陷阱用途的 `.get`(registerAndIntegrate / recovery)不动**(T06 处理)。

**Tech Stack:** Vue 3 + Pinia + Vitest

## 一、新增 `findFolderByPath`(放 [SmartFolder.js](../../../src/models/SmartFolder.js))

与 `countAllFiles` 同类(folder 树的纯查询模块函数),加在 `countAllFiles` 附近:

```js
// 按 path 在 folder 树里查 folder(T05:取代 foldersData.get(path) 的查询用途,为 T06 删 Map 铺路)。
// 纯函数:不改入参,递归 subFolders 匹配 folder.path。返回 folder 或 null。
// ⚠️ ALL_MEDIA 是虚拟文件夹(不在 rootFolder 树),不经此函数查询(switchToAllPhotos 直接用 allMediaFolder)。
export function findFolderByPath(root, path) {
  if (!root || !path)
    return null;
  if (root.path === path)
    return root;
  for (const sub of root.subFolders) {
    const found = findFolderByPath(sub, path);
    if (found)
      return found;
  }
  return null;
}
```

记得在 SmartFolder.js 底部的 `export { ... }` 或各处 `export function` 风格里导出(参照 `countAllFiles` 的导出方式)。

## 三、验证 Map ↔ rootFolder 树同步(关键,迁移前做)

迁移查询源后,`findFolderByPath(fs.rootFolder, path)` 必须能找到原先 `foldersData.get(path)` 能找到的 folder。前提:**所有注册到 Map 的 folder(除 ALL_MEDIA)都挂在了 rootFolder 树上**。逐一核对 `foldersData.set` 的调用点:

| 调用点 | set 的 folder 是否同时挂树? |
|---|---|
| `resetFoldersData`(scanIntegration)| 只 set ALL_MEDIA(虚拟,不在树——**例外**,不经 path 查询)|
| `registerFolderTree`(scanIntegration)| 递归 set + 本身就是从 root 递归调用 → 挂树 ✓ |
| `integrateScanResult`(scanIntegration)| set newSubFolders + `folder.subFolders = result.subFolders` → 挂树 ✓ |
| `registerAndIntegrate`(scanIntegration)| set + integrateScanResult 挂到 parent.subFolders → 挂树 ✓(确认 createResult.folder 的 parent 已挂树)|

- [ ] **Step 3.1:核对同步性**——读上述 4 个 set 点,确认除 ALL_MEDIA 外,set 的 folder 都在 rootFolder 树里。若有反例(某 folder 进了 Map 但没挂树),**停,反馈架构师**(那是潜在 bug,T05 不能盲迁)。

> ALL_MEDIA 例外:`switchToAllPhotos` / `loadFolder` 直接用 `fs.allMediaFolder` 引用,不经 path 查询,所以 `findFolderByPath` 查不到 ALL_MEDIA 无害。

### 遗留 / 风险 / 偏离

1. **机制修正(非 bug,据实记录)**:计划第三节声称 `registerAndIntegrate`「挂到 parent.subFolders → 挂树」。实际 `createFolder` / `registerAndIntegrate` / `integrateScanResult` **都不把新 folder push 进 parent.subFolders**——树是靠 `integrateScanResult` 把 `folder.subFolders = result.subFolders` 写到每个节点逐层连起来的;而 `getFolderData` 创建的唯一 folder 是**根**(= `fs.rootFolder`,即 `findFolderByPath` 的搜索起点)。**结论不变**(Map 与树同步、迁移安全),但挂树机制与计划描述不符。
2. **`getFolderData` 实际只被根 handle 调用**(`loadProject` ← `initProject` / `switchToRoot`,均传根 handle,且调用前 `resetFoldersData` 清 Map)。故:① Query 1(行 152)对根 path,Map 刚清空 → `.get` 必不命中,`findFolderByPath` 也不命中 → 一致走 create 分支;② Query 2(行 163,parent 查找)因根 path 单段、`pathParts.length === 1` 而**实际不可达**(死代码,但迁移对 T06 一致性无害)。两处迁移对**可达状态行为等价**。
3. **顺序偏离**:总规划推荐线性 `T01→…→T04→T05`,T05 表列依赖 T04。本次按用户指示先做 T05——T05 只动 `getFolderData` 的 2 处查询,**不碰 `rootDirty` / `$subscribe`**,与 T04 技术上无依赖,可独立。**T04 仍未做(状态 ☐)**,留待产品负责人/架构师确认顺序。
