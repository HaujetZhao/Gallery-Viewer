# 瞬扫与缓存优化设计(Scan 并发化 + 信任快照)

日期:2026-07-28
状态:已实现

## 背景与第一性原理评估

原 `SmartFolder.scan()` 对目录里**每个文件串行 `await entry.getFile()`**([SmartFolder.js:168-198](../../../src/models/SmartFolder.js))。FS Access API 的目录迭代器 `values()` 只给 `kind`+`name`,size/mtime 只能靠 `getFile()` 取——这是平台强约束。

问题不在"必须 getFile",而在**串行 + 无差别地对待每个文件**:

- **串行**:N 个文件 = N 次串行 IPC,N×单次延迟。5000 文件可达数秒。
- **无差别**:重复打开同一文件夹(已有快照)仍对每个文件 re-IO,只为确认没变。照片是写少资源,这是倒挂。

## 平台事实(决定缓存策略)

- FS Access API **不暴露目录 mtime**(`FileSystemDirectoryHandle` 只有 `kind`/`name`)。**文件夹 mtime 当扫描依据不可行**(拿不到)。
- 即便拿得到,文件系统语义上目录 mtime 也只反映**直接子项的增删改名**,不反映内容编辑、且不向上冒泡——严格弱于"子项名字集合比对"。
- **子项名字集合比对**(`values()` 免费)是平台约束下最优的变更信号:能读、免费、覆盖增删改名(原地同尺寸替换测不出,照片场景可忽略)。

## 决策

### 采取:并发 getFile + 信任快照短路 + 并发可取消后台遍历

> ⚠️ **对最初评审的偏差**:评审阶段提的"两段式"含"纯列表 phase-1(完全不 getFile)"。深读缩略图管线后发现:纯列表会让 phase-1 的 SmartFile 无 File 对象(blobUrl=null),触发跨 6 个文件(含 AudioPlayer/PhotoCard 两个 UI 组件)的 blobUrl 懒建改造,而收益仅是"首开几十 ms"对"并发 getFile 约 150ms"的边际差。故 phase-1 改用**并发 getFile**(仍极快),**完全不碰 blobUrl/UI**,风险面最小。纯列表 phase-1 留作慢盘场景的后续选项(见"未做")。

两个核心目标都达成:

1. **首开快**:`scan()` 把串行 `getFile` 改为并发(`runConcurrent`,默认 32)。串行 N×延迟 → 并发 N/批量×延迟。
2. **重复开零 IO**:`scan({ trust: true })` 先用 `values()` 取当前名字集合,与现有 `this.files`/`this.subFolders` 名字集合比对;**完全一致 → 跳过所有 getFile**,沿用快照里的 size/mtime/md5。名字集合变了 → 只对差异项并发 getFile(新增取元数据,消失的 dispose)。

### 未做(YAGNI,留作后续)

- **纯列表 phase-1 + blobUrl 全懒**:仅在慢盘/网络盘首开有边际收益,代价是 6 文件 blobUrl 改造(含 UI 组件)。等真有慢盘场景再做。
- **`FileSystemObserver` API**(文件变更推送):还在推进/origin trial,稳定版不可靠。等稳定后可省掉后台那轮 `values()` 校验,接口已留好(`scan({trust})` + 取消 token 替换成本低)。
- **缩略图 key 从 md5 换 path+mtime**:会丢失"改名/移动后缓存仍命中",不值得。
- **删 TreeNode**:残废但无害,非性能问题。

## 数据流

- **首次打开**(`openFolderPicker`/无快照 `switchToRoot`):`getFolderData`→`scan()`(并发 getFile 建根)→ 显示 → 后台 `startBackgroundScan`(并发遍历子目录,各 `scan({trust:true})`)→ `saveScan` 快照。
- **重复打开**(有快照):`fromSnapshot` 秒显(零 IO,已有能力)→ 后台 `startBackgroundScan`:各文件夹 `values()` 比名字集合,一致即跳过 getFile(零 IO),有差异才并发 getFile 差异项 → 更新快照。
- **切根中途**:入口换 token,in-flight 的后台遍历在批次间隙检测到 token 失效即退出,不再改旧 store(修原 `startBackgroundScan` 无取消的竞态)。

## 错误处理

- 单个 `getFile` 失败(handle 失效):`runConcurrent` 错误隔离,该项跳过并 warn,不中断其余。
- 后台遍历中权限被撤:token 取消,toast 由调用方处理。

## 测试

- `runConcurrent`:并发上限不超、错误隔离、结果顺序。
- `makeCancelToken`:`cancel()` 后 `cancelled=true`。
- `scan()` 并发:假 dirHandle,断言所有文件被 getFile、结果正确。
- `scan({trust:true})` 信任路:名字集合一致 → **getFile 一次都不调**(用 spy 断言)。
- `scan({trust:true})` 差异路:加一个文件 → 只对新增 getFile,既有不动。
- 取消:遍历中途 cancel → 不再处理后续(在 filesystem 层或用计数断言)。

## 风险与兜底

- **并发 getFile 是否真快**是断言(平台可能内部串行化)。但本设计**不靠并发取胜**:信任短路路本身零 IO,首开只并发读一次。即使并发被平台串行化,信任路的重复开零 IO 仍成立。并发上限做成 CONFIG 可调。
- **原地同尺寸替换测不出**:信任快照已知代价;已有"设置→重载项目"(`reloadProject`,`trust:false`)入口强制全量校验兜底。
