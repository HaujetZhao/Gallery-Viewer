## Part 1:终点审查发现(A–E,执行层问题,非架构层)

架构重构(Phase 1-4)成功:SmartFile 纯身份化、scanFolder 真·纯函数、integrateScanResult 集中副作用、appState/TreeNode/scanned 清除、池 in-flight 去重。59 测试绿。**剩下的是执行层精修。**

### A. `_meta` 与池的**双数据源**(最深残留设计味)

size/mtime 同时存两处:`SmartFile._meta`(为响应式)+ **池 entry**(为 `peek` 共享)。getter `_meta ?? peek` 在糊。

**证据(同步靠人肉,漏一处就 stale):**
- `enrich`、`SmartFile.rename`、`operations.js FileDeleteOperation.undo`:`acquire(...)` 之后**手动** `f._meta = {size, lastModified}`。
- `SmartFile.ensureBlobUrl`:**只 acquire、不写 `_meta`** → 这条路径 size 走 `peek` 兜底,别的走 `_meta`。**同一份 datum 两个真相。**

这是原 blobUrl 耦合的换皮版(从"每条路径管 URL 生命周期"变"每条路径管 _meta↔池 同步")。

**根因**:size/mtime 不该进池(池本只该放 `url`+`file` 为共享)。
**方向**:池只放 `{url, file}`;size/mtime **单一**落在 SmartFile 响应式字段;所有 acquire 处统一写回。消双源、消人肉同步。

### B. enrich 逐个写 `_meta` → **size/date 排序 O(N²) 重排风暴**(性能)

- name 排序(默认)**不受影响**(sort computed 不读 size)。
- size/date 排序时:`_meta` 写在 `runConcurrent` worker 里(异步交错),**每次写触发 `displayFiles` computed 重算**(读全部 `.size`,O(N log N))× N 文件 = 大文件夹首开卡顿/列表反复跳序。
- **方向**:enrich 拆"并发 getFile"+"同步批量写 _meta"——收齐后一个同步循环批量写,Vue 批成一次 flush、sort 只重排一次。
- ⚠️ **待用户验证**:开个几千文件文件夹切 size/date 排序,确认是否真卡(决定优先级)。

### C. `release()` / `owners` 是**死代码**(YAGNI)

[src/fileResource.js](../../../src/services/fileResource.js) 自承"Phase 1 无生产调用方,所有释放走 destroy"。引用计数为"多视图共享"预留,但共享被无限期推迟(owner-based)。留着增加困惑(何时 release 何时 destroy?)。**应删,等真做 handle-identity 共享再加。**

### D. `destroy()` 的 **inflight 边角泄漏**

文件移除时正好在 getFile(inflight),建完仍 `pool.set` → 泄漏一个 url。注释诚实承认未修。罕见但真实。
**方向**:destroy 标记 inflight 取消,建完检查标记不 set(或建完即 drop)。

### E. 次要

- `SmartFile.getActualType()`([SmartFile.js:158](../../../src/models/SmartFile.js#L158))仍 `handle.getFile()` **绕池**(应 `peek(file)?.file` 复用)。
- 响应式行为(`_meta` 触发 sort)**无单测覆盖**,只靠浏览器验收。

### 澄清:非问题

Gallery sort 的 `((a.size ?? Infinity) - (b.size ?? Infinity)) * dir` **括号正确**(进度记录转述漏了外层括号,代码无 bug)。

## Part 2:消除不必要扫描(需求驱动)

### 2.1 平台现实(决定一切)

File System Access API:
- `dirHandle.values()`:吐 `{kind, name}`,**零 per-entry IO,但只有名字**(一次 readdir)。
- `fileHandle.getFile()`:给 size/mtime/数据,**每文件一次 IO**。
- **目录 mtime 读不到**:`FileSystemDirectoryHandle` 无元数据访问器。→ "用文件夹 mtime 判断要不要扫"**不可行**。
- **无变更推送**:`FileSystemObserver` 仍在推进/origin trial,稳定版不可靠。

**结论**:判断"某文件夹内容是否变了",**唯一**便宜的信号是 `values()` 列名 + 名字集合比对(一次 readdir)。无法比这更便宜。判断"某文件内容是否变了",**只能** `getFile()`(每文件 IO)——而这正是我们要避免的。

### 2.2 现状:重复打开已经避免的 IO(信任短路,保留)

scanFolder(trust:true)已做到:
- 名字集合一致 → **零 getFile**,沿用缓存 size/mtime/md5。
- 名字集合变了 → 只对**新增项** getFile,既有项信任保留。
- 缩略图:md5 在 snapshot 里 → IDB 命中 → **零 IO**。

**所以"未变文件"的 getFile 已经消除了。** 这是当前最大的缓存红利,不要动。

### 2.3 仍有的不必要扫描/持久化(3 处浪费 —— 重点)

当前每次打开(`scanAndPersist` → `startBackgroundScan`)做的事,即使**什么都没变**:

| 浪费 | 现状 | 代价(万图/大树) |
|---|---|---|
| **W1 后台全树重扫** | 每个文件夹 `values()` 比名字集合 | N_folders 次 readdir(每次打开) |
| **W2 全量快照重写** | `root.toSnapshot()` 递归序列化整树 + IDB write | O(N_files) 序列化 + 一次大 IDB 写(每次打开) |
| **W3 全树文件计数** | `root.getAllFiles().length` 递归 concat | O(N_files)(每次打开) |

**W1 是用户直觉"后续打开没必要全扫"的所在。** W2/W3 是连带浪费。

### 2.4 解法:从"每次打开全量后台校验"转为"打开即信 + 按需校验 + 变更才持久化"

| 改动 | 做法 | 砍掉的浪费 |
|---|---|---|
| **L1 重复打开跳过后台全扫** | 有 snapshot 时,`switchToRoot` 只 fromSnapshot 显示,**不启动 startBackgroundScan** | W1(重复打开零 readdir) |
| **L2 按需校验(导航触发)** | 用户点文件夹(`handleFolderClick`/`loadFolder`)时,`scanFolder(trust:true)` 该文件夹(+ 可选其直接子目录,供树展开) | 变更检测仍存在,但只在用户要看的地方发生 |
| **L3 变更才持久化(dirty flag)** | 树脏标记;scanFolder/enrich/rename/delete 改了才置脏;`scanAndPersist` 仅 dirty 时 saveScan + 计数 | W2 + W3(未变则零序列化/零写/零计数) |
| **L4 计数增量/缓存** | fileCount 存 snapshot,增删时维护;不每次 getAllFiles | W3 |

**理想终态(重复打开、无变更):fromSnapshot 显示 → 0 readdir / 0 getFile / 0 IDB 写 / 0 全树计数。** 几乎零工作。

**取舍**(必须告知用户):
- L1+L2 后,新增的子文件夹/文件**要等用户导航到才出现**(树计数/空态从 snapshot,导航时校验刷新)。`设置→重载项目` 仍强制全量校验兜底。
- 可选折中:**只 eagerly 校验 root 一层**(一次 readdir 抓顶层增删),深层按需。顶层变化最显眼。

### 2.5 不变的全量场景

- **首次打开**(无 snapshot):仍需逐步扫(可保留后台走,或也改按需——见取舍)。snapshot 是首次扫完后建起来的缓存。
- **重载项目**(手动):仍全量 force-verify(`reloadProject`,trust:false 等价),是"原地同名替换检测不到"的兜底。

## Part 3:万图不卡的核心——Gallery 虚拟化(渲染层,非扫描层)

⚠️ **"不卡"主要是渲染问题,不是扫描问题。** 扫描优化(Part 2)管的是"打开/切换快";**万图不卡管的是"一个文件夹里有上万图时滚动/显示不卡"**。两者是不同杠杆。

### 现状(为什么万图会卡)

[Gallery.vue](../../../src/components/Gallery.vue) **无虚拟化**:`displayFiles` 全量 → 列式 masonry(`cols[i%n].push(f)`)→ **每个文件都挂载一个 PhotoCard + IntersectionObserver + canvas**。万图 = 万个组件 + 万个 observer + 万个 canvas → 内存爆 + 首帧卡 + 滚动卡。

### 方向:只渲染可视区(窗口化)

- **虚拟化 masonry**:跟踪每列累计高度,只渲染视口 + buffer 内的卡片,滚动按需挂/卸。
- 或 **改均匀网格**(CSS grid 固定行高)→ 虚拟化极简(按行切片)。代价:丢 masonry 观感。**设计决策,新窗口与用户定。**
- 配合 **B(批量写 _meta)**:虚拟化后可视卡片少,re-sort 重排成本骤降;但仍建议批量写,避免可视区卡片在 enrich 期间反复重渲。

### 与扫描优化的关系

- Part 2(扫描)让**打开/切换**快;Part 3(虚拟化)让**大文件夹浏览**不卡。**两个都要做才达"万图不卡 + 消除不必要扫描"。**
- Gallery 虚拟化是万图场景**最大的单点收益**,优先级应高于 A–E 精修。

## Part 4:合并优先级规划(round 2 实施顺序)

| 序 | 内容 | 来源 | 风险 | 收益 |
|---|---|---|---|---|
| **R1** | **Gallery 虚拟化**(只渲染可视区) | Part 3 | 中(动 Gallery 布局;masonry vs 网格需定) | **万图不卡——最大单点收益** |
| **R2** | **重复打开跳过全扫 + 按需校验**(L1+L2) | Part 2 | 低-中(改 switchToRoot/handleFolderClick) | 重复打开零 readdir,大树打开瞬完 |
| **R3** | **变更才持久化**(L3 dirty flag)+ 计数缓存(L4) | Part 2 | 低 | 未变则零 IDB 写/零计数 |
| **R4** | **_meta 单一数据源 + 删 release/owners**(A+C 一组) | Part 1 | 中(动池 + 所有 acquire 处) | 消双源 stale 类 bug、消死代码 |
| **R5** | **批量写 _meta 修 sort 风暴**(B) | Part 1 | 低 | size/date 排序大文件夹不卡(与 R1 协同) |
| **R6** | destroy inflight 去泄漏(D)+ getActualType 复用池(E) | Part 1 | 低 | 消边角泄漏 + 一致性 |

**建议**:
- 先 **R1(虚拟化)**——它是"万图不卡"的唯一真正解,收益最大。
- 再 **R2+R3(扫描优化)**——直接回应用户"消除不必要扫描",重复打开近乎零成本。
- **R4/R5/R6** 是精修,可穿插或收尾。R5 与 R1 协同(都让大文件夹顺)。
- 每步独立可验收、可回滚,配测试。UI 主观体验用户自验;客观(DOM/observer 数、computed 重算次数、IDB 写次数)可机械核对。

### 用户需先确认的设计决策
1. **R1 masonry vs 均匀网格**:保 masonry 观感(虚拟化复杂)还是换均匀网格(虚拟化极简)?
2. **R2 重复打开的变更检测策略**:纯按需(导航才校验,新增项延迟出现) / root 一层 eager + 深层按需(折中) / 维持全扫(放弃 W1 收益)?
3. **R5 优先级**:取决于用户是否用 size/date 排序(若只用 name,R5 可降级)。

## 一句话总结

架构重构已稳;round 2 三条线:**① Gallery 虚拟化(万图不卡的唯一真正解,最大收益)② 打开即信+按需校验+变更才持久化(消除不必要扫描,重复打开近零成本)③ A–E 精修(双数据源/死代码/sort 风格/边角泄漏)。** 平台读不到文件夹 mtime,"名字集合比对"是最便宜的变更信号且已用;能再省的是"每次打开的全树 readdir + 全量快照重写 + 全树计数"三处浪费。
